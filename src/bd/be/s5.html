rbookが叩く外部API

rbook\run apiが一覧する9件(GitHub / Azure / Firestore・Firebase / その他)について、rbookのどのコマンドが何を叩き、その先で何が起きているかをソース(rbook / aa)に沿ってまとめたもの。

GitHub 1件 Azure 4件 Firestore・Firebase 3件 その他 1件

IDの読み方

run apiのIDは、run.ymlで定義したグループのkeyと、グループ内での名前順の連番を-でつないだだけ。github-1のような形は9件とも同じ規則で、グループが違うだけ。

ordered = sorted(group["entries"], key=lambda e: e["name"].lower())
for i, entry in enumerate(ordered, start=1):
    rows.append((label, f"{key}-{i}", entry["name"], url, entry["auth"], entry["used_by"]))

URLの実体はrun.ymlに直書きせず、各コマンドが実際に使っている定数(GITHUB_API_BASE等)をrun_api.pyのURL_REFSがそのまま参照している(二重管理を避ける構造)。

GitHub — github-1を叩く5つの呼び出し

GitHub REST APIは「github.comのWeb画面でやることをコードから叩けるAPI」。rbookはGITHUB_PATを添えて次の5箇所で使う。

run reposGET /user/repos — 今“生きている”レポ一覧を直接取得(記憶ではなく実体)
run repo-admin createPOST /user/repos — 新規リポジトリ作成。既定private、--publicで公開
run repo-admin descPATCH /repos/{owner}/{name} — descriptionを更新
run repo-admin pages-enablePOST /repos/{owner}/{name}/pages — GitHub Pagesを有効化
run dumpPOST …/workflows/balog-backup.yml/dispatches — BaLogバックアップを今すぐ起動
run testPOST …/workflows/test.yml/dispatches — CIテストを今すぐ起動
dispatch系だけ2段構え

dumpとtestが投げているのは「今すぐ動かして」というworkflow_dispatchの起動指示だけ。実処理はaa側の.github/workflows/にある。

test.yml workflow_dispatch ← run test

トリガー: push(main) / pull_request(main) / workflow_dispatch。testジョブがNode 20 + Playwright(chromium)でnode --test、test-pythonジョブがPython 3.11でpytest api-tests/(Azure Functionsバックエンドのユニットテスト、テーブルストレージ/Google認証はconftest.pyでフェイクに差し替え)を並行実行。

balog-backup.yml workflow_dispatch ← run dump

Azure — 「インフラを見る窓」と「アプリを使う窓」

4件は同じ提供元というだけで層が違う。azure-1はAzureそのもの(何がデプロイされているか)、azure-2/3/4はそのAzure上で動くbaレジャーというアプリ(何が書き込まれているか)。

azure-1run azure tables/groups/env — az CLIで取得し、x2/tools/04_azure/の「あるべき集合」ymlと突き合わせ、揃っていればOK・想定外なら?を出す
azure-2run ba … — Function App(ab-board-api)の/api/ba本体。読み取りは匿名GET、書き込みはBA_CLAUDE_KEY_PC付きPOST
azure-3run ba wip — 同じFunction Appの/api/s1。WIP作業台の一覧を匿名GETで取るだけ
azure-4run ba tags — 同じFunction Appの/api/s6。BaLogを都度集計し、タグ→ba一覧を軽量に返す(ba-260、フロントはsrc/be/s6.html)

Firestore・Firebase — 同じプロジェクトを2つの角度から

3件とも行き先はFirestore(ab01-9f35a)。caは「アプリの意味(タイトル・本文)」を見る窓、firebaseは「生ドキュメントそのもの」を見るインフラの窓(azure/baの関係と対称)。

firestore-1run ca new/note-add — ca-lane(Cloud Function)への書き込み。CA_CLAUDE_KEYがPC/mobileどちらの鍵と一致したかをサーバー側が判定しレーンを振り分ける
firestore-2run firebase collections/docs — gcloudのアクセストークンでFirestore REST APIを直接叩く。あるべきコレクションと突き合わせる
firestore-3run ca list/show, run firebase collections/docs — 実体は同じFirestore REST。caはSecurity Rulesの匿名GET、firebaseはgcloudトークン付きGET

その他 — 認証なしの1本

残り1件はもっとも単純。run startが、GitHub Pagesで公開している静的テキスト(aa/rbook-start.txt、rbookが前提とする「設計の約束」)を認証無しのGETでそのまま取得して表示するだけ。URLはrun.ymlのdocs.start_url側に外出ししてあり、rbook本体に直書きしない。
